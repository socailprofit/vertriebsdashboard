# Close funnel event history

The journal keeps source revisions, not additive KPI counts. Repeated imports of the same external object and revision produce the same key. A correction to a source object preserves its external identity and replaces the current revision; older revisions remain audit history. An edited booking outcome that no longer says “Termin vereinbart” therefore stops producing a booking. Draft custom activities remain historical metadata and produce no process performance.

The additional journal contains Setter, Closer and attendance activities, plus Opening/Follow-up activities that currently document a booking or whose source ID documented a published booking in any earlier journal revision. Ordinary Gatekeeper/Opening activity remains in the existing raw/facts pipeline. Full Close pagination still supplies the complete source snapshot. The service-role-only `get_close_funnel_booking_source_ids()` reads all immutable revisions, including superseded and withdrawn ones, so a later draft, deleted booking outcome or reactivation stays auditable. An activity that was only ever a draft booking does not create a historical booking marker. Calendar journal scope is unchanged.

## Sources and reliable fields

| Source | External identity | Event time | Relevant data |
| --- | --- | --- | --- |
| Custom sales activity | Close activity `id` | `activity_at` | Activity type, published/draft, explicit result fields, author, source creation/update time |
| Calendar meeting | Close meeting `id` | `starts_at` | `ends_at`, lead/contact IDs, owner, participant IDs/RSVP, status, source creation/update time, calendar UIDs, documented booking link |
| Lead status activity | Close activity `id` | `activity_at` | `old_status_id`, `new_status_id`, author, source creation/update time |
| Sales opportunity | Opportunity `id` | `date_won` for Won | Pipeline/status IDs, status type, source creation/update time, observed lead attribution |

Lead-status API: `GET /activity/status_change/lead/` supports `_fields`, `_limit`, `_skip`, `date_created` range filters and `activity_at` range filters. Its documented list endpoint does **not** expose a `date_updated` range filter. Do not silently use a creation-time window as proof that all historical corrections were fetched. [Close endpoint documentation](https://developer.close.com/api/resources/activities/lead-status-changes/list).

Close's separate Events API is a change log with limited retention and consolidation of rapid updates. It is not a full retrospective source of every intermediate status. A future cursor-based correction reader must persist its cursor and detect gaps; it must not invent missing intermediate statuses. [Close Events documentation](https://developer.close.com/api/resources/events).

## Time, authorship and privacy

- The normalizer has no month or three-month reporting cutoff. Old activity evidence and already known future meetings are retained; the process adapter only emits observed performance through `dataAsOf`.
- Calendar status `completed`, RSVP acceptance, lead status and an activity's booking date do not prove a Setter/Closer conversation occurred.
- The actual author of an explicit Setter/Closer activity supplies the corresponding actor ID. The booking author does not automatically become the Setter. Opportunity role fields are marked `lead_fields_at_sync`; they are an observed attribution, not proof of historical ownership.
- `date_won` can be a date without a time. The journal retains the original date, its existing reporting-mapper timestamp and precision `date`. The process adapter uses Berlin midnight as a computational date anchor so an already known sale counts on its day, including mornings. Neither anchor is an exact Close signing time; the UI must show only its date. A date-only terminal outcome cannot prove it preceded a new booking on the same day.
- Only the Sales pipeline's verified `Kunde` Won status produces an acquisition candidate, and the configured deal-type field must be `Neukunde` or absent, consistent with the existing reporting definition. Explicit upsell/renewal does not. The process adapter selects the earliest acquisition candidate per lead from the supplied complete Won history, with stable tie-breaking by external ID. A custom CC1/CC2 “sold” result produces `closer_sold`/`cc2_sold` for the pending-Won state; it does not itself create another new customer.
- Names, email addresses, titles, notes and unrelated custom fields are omitted. IDs and explicit configured sales outcomes remain.

## Persistence contract

The payload schema emitted by `prepareFunnelEventSnapshot` is the contract for the additive migration: `lead_id`, `event_type`, `occurred_at`, nullable `meeting_id`, `previous_status`, `new_status`, `setter_id`, `closer_id`, `source_event_id`, `source_kind`, `source_updated_at`, `source_revision`, `payload`.

`source_kind + source_event_id` identifies an external object. `source_revision` is SHA-256 of canonical permitted fields including the source's update timestamp. The sync's observation time is not hashed. Array ordering of participants and calendar UIDs does not create spurious revisions. Conflicting page versions of one source ID fail the snapshot rather than selecting an arbitrary winner.

If a pre-existing source or refreshed lead metadata was updated after the snapshot cutoff while pages were loading, the run fails with the fixed category `source_snapshot_changed`. The previous committed funnel remains authoritative until the next scheduled sync. Newly created sources after the cutoff simply wait for that next snapshot. This avoids applying a correction before the advertised data cutoff.

The database must maintain one current revision per source identity, preserve superseded revisions, and mark missing identities withdrawn only after all pages for the declared source coverage succeeded. For a bounded lead-status creation window, withdrawal is limited to previously stored status objects whose **creation time** is in that window. Older rows remain retained; absence from the window proves nothing about their deletion. The normalizer deliberately does not perform database deletion or infer completeness.

`toProcessEvents` accepts current, non-withdrawn revisions. It emits explicit sales outcomes for deterministic process attribution. Status transitions emit `status_changed` only. Negative attendance still requires the separate calendar/time attribution rule; merely importing a cancellation or No-Show activity does not make every appointment of that lead negative.

## API load and retry behavior

The automatic metadata refresh reads batches of at most 100 exact lead IDs through the read-only `POST /data/search/`, using only the required fields. It follows every cursor and requires every requested identity before the snapshot can commit. This removes the former burst of individual Lead GET requests. The endpoint and its ID query, field projection and cursor semantics are documented in [Close Advanced Filtering](https://developer.close.com/api/resources/advanced-filtering).

Every Close read in one sync shares a paced admission queue and rate-limit cooldown. HTTP 429 waits for the advertised `Retry-After`/`RateLimit.reset`; successful responses with no remaining allowance also pause subsequent reads. Four retries, a 30-second individual request timeout and a 130-second read budget bound the run. The total budget leaves 20 seconds before Supabase's documented 150-second request limit for processing and commit; it is a ceiling, not a latency guarantee. Other HTTP errors are not retried. A budget failure leaves the previous funnel snapshot intact. Resource diagnostics report only the redacted path, count, pages and elapsed milliseconds at completion/failure and every 25 pages. Timeouts identify the redacted path and distinguish request timeout from total budget exhaustion. Dynamic object IDs and query strings are removed from public error paths. [Close Rate Limits](https://developer.close.com/api/overview/rate-limits), [Supabase Limits](https://supabase.com/docs/guides/functions/limits).

Persistent snapshot SELECTs have a 15-second request timeout. Only PostgREST `PGRST303` results are retried twice, after 500 and 1,500 milliseconds, with identical authorization. JWT validation stays enabled; persistent failures still stop the run. Logs use fixed classifications such as `issued_in_future` or `expired`, never token/claims contents. Phase checkpoints record counts and elapsed time in function logs and `sync_runs.metadata`; diagnostic writes have a three-second timeout and cannot alter the core commit decision. [Supabase error-code definitions](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/api/rest/postgrest-error-codes.mdx).

Dry-run and write now build the same snapshot envelope before any KPI writes. `funnel.payloadBytes` and the `snapshot_prepared` phase report exact serialized UTF-8 bytes for each fixed section and the whole `p_snapshot` envelope, plus section row counts in the dry-run result. These diagnostics contain no source IDs or field contents. They measure transport size; they do not establish the production timeout's cause.

## Bounded snapshot upload

`close-funnel-upload.ts` prepares the same 16-section snapshot as an immutable manifest and row-aligned JSON chunks. The complete RPC request body, including text escaping, stays below 256 KiB. Each section declares its row count and ordered chunk hashes; SQL verifies SHA-256 against the exact UTF-8 JSON bytes using Postgres's native `sha256(bytea)`. No JSON formatting conversion is used for the checksum. Empty sections are explicit `[]` chunks. A single oversized row, more than 1,024 chunks or more than 64 MiB of payload stops the upload.

Migration `20260908162829_stage_funnel_upload_chunks.sql` adds private upload/chunk tables and service-role-only Begin, Put, Finalize and Cleanup RPCs. Reporting does not read these tables. The service role itself receives only the narrow RPC permissions, not direct table access. A stable run UUID plus the unchanged manifest identifies a retry; conflicting declarations or chunk contents are rejected. Upload retries never change authorization or retry business/permission failures. At most three chunks are sent concurrently by default, and every worker settles before Finalize. Progress contains only bounded counts, bytes and elapsed time.

Finalize receives only the run UUID, locks that upload, verifies completeness and every stored checksum, assembles the snapshot inside Postgres, and invokes the existing `reconcile_close_funnel_payload` transaction unchanged. Stale snapshots and invalid source/calendar relationships still roll back all reporting writes. After success, the immutable manifest plus result remain for one day so an uncertain successful response can be retried without another publication. Payload cleanup occurs separately from the final publication transaction: the helper attempts up to eight batches of 16 committed chunks within an independent two-second budget. A maintenance failure leaves the committed result successful, and a later successful run drains the oldest remaining chunks. Unfinished uploads expire 30 minutes after their snapshot cutoff. Begin removes at most two expired uploads; a service-only cleanup RPC can remove a separately bounded batch. No additional scheduler is introduced. Migration `20260908163718_defer_funnel_chunk_cleanup.sql` removes only the inline payload deletion from Finalize and adds the bounded service-only maintenance RPC; all source and publication guards remain unchanged.

Local SQL tests cover interruption, conflicting/repeated requests, byte corruption, missing chunks, expired/stale snapshots, real role denials, finalization retry and source-validation rollback. A PGlite benchmark using 6,543 journal events, 1,032 processes, 3,055 meetings and 783 raw/fact rows transported 13,412,142 JSON bytes across 66 requests; the largest request was 261,160 bytes. Local finalization was 699–810 ms, including unchanged reconciliation. These figures compare local implementations and are not proof of production latency; the live controlled run must verify that separately.
